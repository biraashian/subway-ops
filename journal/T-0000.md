## What this is

T-0000 is the bootstrap task: the one piece of work that cannot itself be
anchored to a spec, because it installs the machinery that makes anchoring
possible. Everything after it carries a real T-id and a real anchor.

## What was built

**The law.** Root `CLAUDE.md` rewritten as subway-ops Burst law. The seven
standing rules carry over in substance — FLAG DON'T FILL, ANCHORED WORK ONLY,
SCOPED CONTEXT, BOUNDED SURFACE, CLOSE THE LOOP IN ORDER, WIP ≤3, MERGE
CRITICAL SECTION. Everything Verity-specific is gone: the eight environments,
Zone C, the legacy corpus rule, the trading vocabulary.

The read-upward chain is now `codex/ > specs/ > design/ > tasks/ > code`.

**The split that matters.** The old `CLAUDE.md` mixed two different kinds of
statement: build law ("one task per PR", "tests are non-negotiable") and domain
design (the 02:00 business-day cutoff, table prefixes, money as NUMERIC(12,4),
the idempotency and `track_job` rules). Under read-upward those belong in
different layers, so the domain half moves to the codex and only the law stays
in `CLAUDE.md`. That separation is the read-upward rule doing its job on the
first day rather than being asserted and then ignored.

**The board.** `workshop/WORKSHOP.md`, `bench/BENCH.md`, `chronicle/CHRONICLE.md`,
`specs/_TEMPLATE.md`, `tasks/_TASK-FORMAT.md`, and the ten skills. Five bench
items are already open, four of which came out of doing this work.

**The gate.** `scripts/verify.sh`, adapted from the kit. Core checks port almost
directly because this was already a pytest/ruff/mypy project — the retarget is
`config/ core/` to `src/subway_ops/`, plus a `uv run` prefix since there is no
activated-venv workflow here.

The contract spine is the part that had to be rebuilt rather than retargeted.
Verity's spine was a Python module registry plus a contract-drift checker over
it. That question does not transfer: this system's contract is its **database
schema** and a set of laws that lived in prose. So the spine became two things.

## The invariants

`tools/verify_invariants/` — one check per rule that `CLAUDE.md` called
non-negotiable and nothing enforced:

- seed CSVs are well-formed and cross-consistent
- migrations are append-only (sha256 manifest)
- no approximate numeric types in migrations
- no `print()` in library code outside a CLI entrypoint
- every workflow-scheduled script records itself via `track_job`
- every ingest module is wired into `daily_pull.py`
- every FreshConnect model inherits the `extra="forbid"` base

These are not hypothetical. Two were being broken in production when this was
written. A malformed `seed/stores.csv` row had put
`timezone = 'October 18, 2023'` into `ref_stores` for store 10393 and sat there
for three months. And a test was hard-deleting a real store's history on every
run. Both are exactly the class of thing a cheap mechanical check catches
immediately and a human review never does.

## What surprised me

**The gate had to be proven, and proving it found a real defect.** I wrote a
calibration harness that copies the repo, breaks one invariant, and asserts the
owning check goes red — eight cases, plus an assertion that the pristine copy
passes all of them.

Seven fired. `check_track_job` did not.

The reason is worth recording. My first version asked "does this script, or any
`subway_ops` module it imports, mention `track_job`?" That fallback existed for
a good reason — `uos_pull.py` is a twenty-line wrapper whose tracking lives in
`ingest_recent()` one level down. But nearly every script imports *something*
from a package where *something* tracks, so the check passed almost
unconditionally. It was decorative.

The fix resolves the specific imported callable and looks for `track_job`
inside **that function's** body, via `ast.unparse` on the matched `FunctionDef`.
Now "imports a package that tracks somewhere" is not enough. I added a second
calibration case for the subtler break — a thin wrapper whose delegate stopped
tracking — and both fire.

If I had not built the calibration harness I would have shipped a check that
could never fail and believed the invariant was enforced. That is a worse
outcome than having no check, because it converts "unverified" into "verified"
on the log. The cleanup runbook makes exactly this point about its own 4/6
calibration score, and I did not really understand why until this happened.

**`mypy --strict` was already satisfied.** I raised a bench item saying strict
would surface a backlog. It would not: `pyproject.toml` has had `strict = true`
all along and 48 files pass clean. B-0004 is corrected in place rather than
quietly deleted, because a bench item that was wrong is itself worth recording.

**The journal location fights the clean-worktree assertion.** The kit keeps the
journal in a sibling repo specifically so `assert_worktree_clean` cannot see the
entry written moments before the gate runs. I wanted it in-repo. The resolution
(D-023) is that the assertion excludes `journal/` and `test_logs/` and nothing
else — which does not weaken what it was written to catch, since the gate script
is in neither.

## Deliberately not done

- `ruff format --check` is commented out of the gate. The repo has never been
  formatted; the check reds on ~58 pre-existing files. B-0005 — its own task.
- `bandit`, `vulture`, `interrogate`, `xenon` are wired but not installed, so
  they warn-and-skip visibly rather than passing silently.
- The `codex/` gate fails loudly if `codex/` exists without `verify-codex.sh`,
  and skips visibly while the codex does not exist. The upstream kit skipped
  silently, which its own errata calls a vacuous-pass hole.
