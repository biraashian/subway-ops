# T-0016 — DB tests seed their own stores and namespace per run

Date: 2026-08-18
Branch: `forge/T-0016`
Type: bug_fix
Anchors: D-039, D-040 (B-0035, B-0036)
Decisions: none

## What was built

`tests/conftest.py` grows from a one-line docstring into the isolation
machinery: a per-process `SESSION_TOKEN`, an `ns()` function that namespaces a
file's marker to the run, and a `synthetic_store_factory` fixture that creates
stores and drops them.

Ten DB-backed test files now pass their markers through `ns()`.
`tests/test_people_schema.py` stops reading real store numbers.
`tests/test_test_isolation.py` tests the machinery itself.

## The evidence, which is the whole point

B-0036 was raised with a measurement, so the fix is reported against the same
measurement. Two runs of `tests/test_people_wages.py` started together:

```
before T-0016   run A : 3 failed, 21 passed, 2 errors
                run B : 4 failed, 19 passed, 4 errors
                serial: 25 passed

after  T-0016   run A : 25 passed
                run B : 25 passed
```

That is the defect gone rather than the defect described. It mattered because
`/audit` re-runs the gate by design: earlier today a pre-merge run of `9583f0f`
exited 1 while the audit's run of the *same commit* exited 0, and the difference
was that they overlapped.

## Why the token is a module constant and not a fixture

Every one of these files declares its marker at module level —
`MARK = "t0004-selftest"`, `KIND = "t0003_selftest"` — evaluated at import,
where no fixture exists. So `ns()` is a plain function and `SESSION_TOKEN` is
computed once at import of `conftest`.

The token is `f"{os.getpid()}{uuid4().hex[:6]}"`. The PID is there so a human
finding a stray row can tell which process left it. The random suffix is there
because PIDs are recycled and two runs a few seconds apart could otherwise
collide — which is exactly the failure being fixed, one level down. It is short
because it is concatenated into `clerk_id` and `store_number` values, and a
long marker starts bumping into column widths and into `LIKE` patterns.

## The last real-store reader, and why it survived an audit

`tests/test_people_schema.py` took the two lowest real store numbers out of
`ref_stores` to satisfy a foreign key. T-0004's audit passed it, and B-0035
noticed it only in passing while looking at T-0007.

It survived because it looked harmless, and it nearly was: those tests never
write staging rows against the store, they only need a `store_number` that
exists. The reasoning "we only read it" is exactly the sort of exception that
feels obviously fine at the keyboard and is invisible three files later. codex
13 has no read-only exemption, and a rule with an undocumented exception is a
rule nobody can apply.

Both sites now seed `T-PPL-S{i}-{token}` with `is_active=false` and drop it in
teardown. `is_active=false` is not cosmetic: codex 13 requires it so the ingests
cannot pick the store up and start writing real-looking rows against it.

## The grep test

`test_no_db_test_selects_a_real_store_number` scans every `test_*.py` for
`SELECT store_number FROM ref_stores`. That is not a behavioural test and I want
to be honest about what it is: a lint rule wearing a test's clothes, aimed at a
failure mode that is social rather than technical — someone writes the
convenient thing in a file nobody reviews closely, and it passes.

It is scoped so that reads *about* `ref_stores` still pass. `test_reference_data.py`
counts rows and checks a join; `test_mart_recon_weekly.py` deletes its own
synthetic store. Neither borrows a real store's identity, which is the thing the
convention actually forbids. A guard that failed those would be deleted within a
month, and then it would guard nothing.

## What I did not do

**No lockfile.** B-0036's option B — serialise the gate so only one run touches
the database at a time — was explicitly not adopted, and D-040 records why: it
slows the gate in exactly the situation where two things are trying to make
progress. Adding it here because it would also work would be filling a decision
the founder declined.

**No adhoc skip-count reporting.** B-0030's option B, also declined. Adhoc still
will not say what it skipped. That hole stays open by choice and the record says
so.

**No production code touched.** The task's first FORBIDDEN_ACTION, and nothing
came close to needing it.

## What surprised me

That ten files carried the same defect and none of them looked wrong. Every one
followed the local convention faithfully — a marker, a teardown filtering on it,
rows namespaced so they could not collide with real data. The convention was
right about everything except that a marker names a *file* and the thing that
needs distinguishing is a *run*. Nobody wrote a bug; the pattern had a hole in
it and got copied ten times.

Also: this task exists because of two decisions made after two separate
incidents, and both incidents happened to me today. Writing the fix took under
an hour. Finding out it was needed cost a production write of 405 rows, twice, a
gate that contradicted itself, and two audits. The ordering there is the
argument for doing harness work before the thing it protects, not after — and
T-0011 is still queued, which is the version of this that makes all of it moot.
