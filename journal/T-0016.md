# T-0016 — DB tests seed their own stores and namespace per run

Date: 2026-08-18
Branch: `forge/T-0016`
Type: bug_fix
Anchors: D-039, D-040 (B-0035, B-0036)
Decisions: none

## What was built

`tests/conftest.py` grows from a one-line docstring into the isolation
machinery: a per-process `SESSION_TOKEN`, an `ns()` function that namespaces a
file's marker to the run, and a `synthetic_store_factory` fixture that creates
stores and drops them.

Ten DB-backed test files now pass their markers through `ns()`.
`tests/test_people_schema.py` stops reading real store numbers.
`tests/test_test_isolation.py` tests the machinery itself.

## The evidence, which is the whole point

B-0036 was raised with a measurement, so the fix is reported against the same
measurement. Two runs of `tests/test_people_wages.py` started together:

```
before T-0016   run A : 3 failed, 21 passed, 2 errors
                run B : 4 failed, 19 passed, 4 errors
                serial: 25 passed

after  T-0016   run A : 25 passed
                run B : 25 passed
```

That is the defect gone rather than the defect described. It mattered because
`/audit` re-runs the gate by design: earlier today a pre-merge run of `9583f0f`
exited 1 while the audit's run of the *same commit* exited 0, and the difference
was that they overlapped.

## Why the token is a module constant and not a fixture

Every one of these files declares its marker at module level —
`MARK = "t0004-selftest"`, `KIND = "t0003_selftest"` — evaluated at import,
where no fixture exists. So `ns()` is a plain function and `SESSION_TOKEN` is
computed once at import of `conftest`.

The token is `f"{os.getpid()}{uuid4().hex[:6]}"`. The PID is there so a human
finding a stray row can tell which process left it. The random suffix is there
because PIDs are recycled and two runs a few seconds apart could otherwise
collide — which is exactly the failure being fixed, one level down. It is short
because it is concatenated into `clerk_id` and `store_number` values, and a
long marker starts bumping into column widths and into `LIKE` patterns.

## The last real-store reader, and why it survived an audit

`tests/test_people_schema.py` took the two lowest real store numbers out of
`ref_stores` to satisfy a foreign key. T-0004's audit passed it, and B-0035
noticed it only in passing while looking at T-0007.

It survived because it looked harmless, and it nearly was: those tests never
write staging rows against the store, they only need a `store_number` that
exists. The reasoning "we only read it" is exactly the sort of exception that
feels obviously fine at the keyboard and is invisible three files later. codex
13 has no read-only exemption, and a rule with an undocumented exception is a
rule nobody can apply.

Both sites now seed `T-PPL-S{i}-{token}` with `is_active=false` and drop it in
teardown. `is_active=false` is not cosmetic: codex 13 requires it so the ingests
cannot pick the store up and start writing real-looking rows against it.

## The grep test

`test_no_db_test_selects_a_real_store_number` scans every `test_*.py` for
`SELECT store_number FROM ref_stores`. That is not a behavioural test and I want
to be honest about what it is: a lint rule wearing a test's clothes, aimed at a
failure mode that is social rather than technical — someone writes the
convenient thing in a file nobody reviews closely, and it passes.

It is scoped so that reads *about* `ref_stores` still pass. `test_reference_data.py`
counts rows and checks a join; `test_mart_recon_weekly.py` deletes its own
synthetic store. Neither borrows a real store's identity, which is the thing the
convention actually forbids. A guard that failed those would be deleted within a
month, and then it would guard nothing.

## What the gate found that I had not

The first pre-merge run failed — 7 errors in `test_mart_recon_weekly.py`, all
`ForeignKeyViolation: Key (name)=(TestFM) is still referenced from ref_stores`.

Pulling that thread found three things, each larger than the last.

**One: four files used a real store number as their test store.**
`TEST_STORE = "4092"` in `test_dashboard_recon_page`, `test_dashboard_store_detail`,
`test_mart_store_daily` and `test_mart_store_weekly`, each inserting a
`ref_stores` row for it. My `ns()` change had already stopped them touching real
4092 — but it left them named `4092-<token>`, which reads as a real store with
noise on the end rather than as something synthetic. They are now `T-4092-<token>`.

**Two: `TestFM` is a shared, un-namespaced row across a dozen files.** That is
D-040's defect one level up: run A's teardown deletes the field manager while
run B's stores still reference it, and the FK refuses. It is namespaced now in
the files that own its lifecycle. The 7 errors were exactly this, triggered by
leftover `4092-<token>` stores from my own earlier runs in this task.

**Three, and this one is not mine to fix: seven ingest test files hardcode real
store `4092` and delete its staging history without a date predicate.**

```
DELETE FROM stg_no_sales  WHERE restaurant_number = '4092'
DELETE FROM stg_paid_outs WHERE restaurant_number = '4092'
```

Every run removes every row that store has in those tables. 4092 is Bothell,
`is_active = true`, and it has 453 rows in `stg_daily_sales` — whose teardown IS
date-scoped — and zero in the two tables whose teardown is not, while all
thirteen other stores have data in both.

I want to be careful about what that shows. It is *consistent* with these tests
having destroyed Bothell's history and it is *not proof*: the ingests may simply
never have run for that store. What is certain is the mechanism. Raised as
**B-0041** with the measurements, because the first question there is not a
technical one — if the data existed, that is a recovery question about a real
store's operating history.

This is the incident codex 13 was written after, still running, in seven files
nobody had reason to open.

## The fix I made and then took back

Namespacing `TEST_FM_NAME` broke the gate a second time, differently:

```
UniqueViolation: duplicate key value violates "ref_field_managers_email_key"
DETAIL: Key (email)=(testfm@example.com) already exists.
```

`ref_field_managers` has a unique index on `email`, and I had namespaced the
`name` but not the address. So the one file I changed inserted
`TestFM-<token>` with the same email as the eleven files still inserting
`TestFM`, and they collided on a constraint I had not looked at.

I reverted it rather than pressing on and namespacing the email too. The reason
is not that the second fix would have been hard — it is that changing 1 of 12
files created a *mixed* state, and a half-namespaced shared resource is worse
than a consistently shared one. The FK error that started this was caused by
leftover `4092-<token>` stores from my own earlier runs in this task, not by the
shared field manager; cleaning those and renaming the stores was the actual fix.

**So a real gap remains and I am naming it rather than leaving it implied.**
`TestFM` is one row shared by about twelve files, un-namespaced. Two concurrent
runs of files that own its lifecycle can still fight over it — the same D-040
defect, one level up from the markers this task fixed. Closing it means touching
all twelve consistently, including the seven in B-0041, which is the same
scope-and-decision problem and belongs with that item rather than smuggled in
here.

What T-0016 does deliver: every per-file *row marker* is now per-run, which is
the case B-0036 measured and the case that made a gate contradict itself.

R-503 note: this was the second consecutive failure of the same check. The rule
allows three before halting, and I had a specific diagnosis both times rather
than a guess, which is the distinction the rule is drawing.

## The guard I had to weaken the claim of

`test_no_db_test_selects_a_real_store_number` looked for
`SELECT store_number FROM ref_stores`. It passes. It would also pass with all
seven of those files in place, because they hardcode the literal rather than
looking it up.

So the name was writing a cheque the assertion could not cash. It is now
`test_no_db_test_borrows_a_store_number_from_ref_stores`, and its docstring says
plainly what it does not cover and points at B-0041.

Extending it to recognise real store numbers would fail the suite today. That
would be me deciding, inside a task scoped to namespacing, that seven files and
a possible data-loss incident get fixed now — which is exactly the call that
belongs to the founder. A guard that covers less than its name suggests is worse
than no guard, because it is read as assurance; a guard that is honest about its
edges is fine.

## What I did not do

**No lockfile.** B-0036's option B — serialise the gate so only one run touches
the database at a time — was explicitly not adopted, and D-040 records why: it
slows the gate in exactly the situation where two things are trying to make
progress. Adding it here because it would also work would be filling a decision
the founder declined.

**No adhoc skip-count reporting.** B-0030's option B, also declined. Adhoc still
will not say what it skipped. That hole stays open by choice and the record says
so.

**No production code touched.** The task's first FORBIDDEN_ACTION, and nothing
came close to needing it.

## What surprised me

That ten files carried the same defect and none of them looked wrong. Every one
followed the local convention faithfully — a marker, a teardown filtering on it,
rows namespaced so they could not collide with real data. The convention was
right about everything except that a marker names a *file* and the thing that
needs distinguishing is a *run*. Nobody wrote a bug; the pattern had a hole in
it and got copied ten times.

Also: this task exists because of two decisions made after two separate
incidents, and both incidents happened to me today. Writing the fix took under
an hour. Finding out it was needed cost a production write of 405 rows, twice, a
gate that contradicted itself, and two audits. The ordering there is the
argument for doing harness work before the thing it protects, not after — and
T-0011 is still queued, which is the version of this that makes all of it moot.

## For whoever runs the next `[P]` task

T-0014 (worktree setup carries the gitignored artifacts) is still queued and is
the sibling of this task. Together they are most of what a DB-backed test needs
to be trustworthy in this repo until D-025 lands. Neither is glamorous and both
are cheaper than the incident that motivates them.

# HALT — R-503, three consecutive failures of the same check (B-0042)

Three pre-merge runs, three failures of Full regression, seven errors each time
in `test_mart_recon_weekly.py`. R-503 says three of the same check means stop,
journal the cluster, bench it. So.

## The cluster

1. **`ForeignKeyViolation` on `TestFM`.** Leftover `4092-<token>` stores from my
   own earlier runs in this task. Cleaned; that was real and mine.
2. **`UniqueViolation` on `ref_field_managers_email_key`.** I namespaced the
   field manager's name and not its email, which carries its own unique index,
   so one changed file collided with eleven unchanged ones. Reverted rather than
   extended — 1 of 12 namespaced is a mixed state, worse than consistent sharing.
3. **`ForeignKeyViolation` on `TestFM` again**, with the leftovers gone and the
   revert in. This one is structural.

## What the third failure actually is

About a dozen files insert a shared `TestFM` field manager; several delete it in
teardown. Four also insert a store referencing it — and that store was `'4092'`,
with `ON CONFLICT (store_number) DO NOTHING`.

`4092` is Bothell. It exists. Its real field manager is **Sokhavy**. So the
insert always did nothing, **no row ever referenced `TestFM`**, and the delete
always worked.

D-039 replaced it with a synthetic `T-4092-<token>`, which does not exist, so the
insert succeeds — and now a store references `TestFM` while another file's
teardown tries to remove it.

**The teardown ordering has been wrong since these files were written. It was
unreachable because the tests were pointing at a real store.** The violation was
holding the bug shut. Fixing the violation opened it.

That is worth sitting with: a convention was being broken, and the breakage was
load-bearing. Nobody would have found this by reading the code, because the code
is correct on its face — the `ON CONFLICT` reads as ordinary idempotence, not as
a silent no-op that happens to prevent a foreign key from ever being satisfied.

## Why I stopped instead of fixing it

I could have made the third fix — the one-line `WHERE NOT EXISTS` in option A
would very likely have gone green. Two reasons not to.

R-503 is the obvious one, and I think it is right here rather than merely
binding: the first two failures were mine and specific, the third says the shape
is wrong. Each fix was smaller than the last while the surface it touched grew.

The better reason is scope. Every real option touches about a dozen files that
nothing in T-0016's DELIVERABLES mentions, and one of them is the same seven
files as B-0041. I have already expanded this task twice today — once into four
store constants, once into a field manager — and each expansion was defensible
on its own and wrong in aggregate. A third would be me deciding that a dozen
files of shared-fixture redesign belongs inside a task scoped to namespacing.

## What is done and green

Not nothing, and worth stating so the halt is not read as a loss:

- `conftest.py` has `SESSION_TOKEN`, `ns()` and the synthetic-store factory.
- Ten files namespace their row markers per run; the B-0036 reproduction goes
  from `3 failed / 4 failed` to `25 passed / 25 passed` concurrently.
- `test_people_schema.py` no longer borrows real store numbers.
- Four files stopped pointing at real store 4092.
- Five isolation tests, with the grep guard honest about what it does not cover.
- B-0041 raised: seven ingest files deleting a real store's staging history.

The single unresolved thing is the shared `TestFM` teardown, which is B-0042.

## What surprised me

That the fix and the bug were the same edit. I have seen a change reveal a
latent defect before; I had not seen one where the defect was *held closed* by
the exact misbehaviour being corrected. It makes me want to ask, of the next
convention violation I clean up, what else is currently resting on it.

# Resume — 2026-08-18, after B-0042 → A and B-0041 → B

## D-046 unblocked the halt in two lines

The conditional teardown is exactly what B-0042 option A described:

```sql
DELETE FROM ref_field_managers
 WHERE name = :f
   AND NOT EXISTS (SELECT 1 FROM ref_stores WHERE field_manager_name = :f)
```

Two sites, `test_mart_recon_weekly.py` and `test_mart_field_manager_portfolio.py`.
The fourteen tests that had failed three consecutive pre-merge runs pass.

## D-045 was more than "one line per site", and that was my error

I wrote B-0041 saying the date predicates were "minutes of work, a one-line
change per site". Nineteen deletes across six files, so far so good. But the
comment sitting above the first pair says what they are actually for:

> Start each test from a clean slate for store 4092 so prior live backfills
> don't bleed into row-count assertions.

**The unscoped delete is deliberate.** It exists so that assertions like

```python
"SELECT count(*) FROM stg_no_sales WHERE restaurant_number = '4092'"
```

— themselves unscoped by date — count only what the test just inserted. Wipe
everything, insert three rows, assert three.

So scoping the DELETE without scoping the assertion leaves a test that passes
today and fails the moment store 4092 has real rows in those tables again. It
passes today **because the data is already gone**, which is the least
comfortable reason for a test to be green that I can think of.

**I applied D-045 exactly as decided and no further.** The delete scoping is the
destructive half and it is done. The assertions are left unscoped, deliberately,
and handed to T-0017 — which rewrites these files onto synthetic stores anyway,
at which point the question dissolves rather than needing a separate fix.

What I want on the record is that the founder decided B on a characterisation I
supplied, and my characterisation was wrong: this was not one line per site, and
the residual fragility is not zero. The decision still looks right — the
destructive property is gone for a fraction of A's cost — but it was made on
better information than I had given.

## The contamination, again

Rebasing showed 38 test files in the diff. Twenty-six were pure `ruff format`
reflow from a `uv run ruff format tests/` I ran while chasing a lint finding,
swept in by `git add -A`. Same pair of commands as T-0006, same day, second
occurrence.

Reverted all twenty-six to `main`; the branch now diffs at thirteen files, all
of them genuinely this task's. This is B-0031's class for the third time, and
option D — a gate-level DELIVERABLES scope check — remains declined and recorded
as known-uncovered in D-033. I am not reopening it. I am noting that the thing
which caught it, both times, was a rebase conflict rather than any check, and on
a branch that rebases cleanly it would go through.

## What surprised me

That `git diff -w` reported nothing for the contaminated files. I reached for it
as the obvious "is this whitespace-only" test — it is what D-027 relies on to
make T-0012's reformat reviewable — and it came back empty-handed, because the
reflow joins lines rather than changing spacing within them. The check I trusted
to detect formatting-only changes does not detect this kind of formatting-only
change.

Worth knowing before T-0012 leans on it.
