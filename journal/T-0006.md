## The halt — B-0037

AC-024: "IF a terminated person clocks in again, THEN the roster service SHALL
reactivate the **same** person row and SHALL NOT create a new one." AC-022 says
termination sets `termination_date` **and** `is_active = false`.

"Reactivate" plainly means `is_active = true`. Nothing says whether
`termination_date` is cleared, and both readings are defensible:

- Clearing it makes AC-024 the inverse of AC-022 and leaves a coherent row.
- Keeping it preserves the fact that the person once left, at the cost of a row
  reading `is_active = true` alongside `termination_date = 2025-03-01`, which
  any consumer filtering on `termination_date IS NULL` will misread.

I went looking for the answer before benching. codex 06 "Leaving" is explicit
that a returning employee is the same row reactivated, and silent on the
columns. §6's edge table settles which row, not what the row then says. codex 07
matters here: the I-9 retention rule is a *later-of* — three years from hire or
one year from termination — and it reads `termination_date`. codex 00 says
corrections are new rows with a reason, though a rehire is arguably a new event
rather than a correction.

`ref_employees` has one `termination_date` column and no history table, so
whichever reading is chosen is the only record of the event.

**Why I benched instead of picking.** I could argue either side well, and this
session has now taught me twice that arguing a position well is not evidence it
was mine to take — D-037 records exactly that, in my own words. The tiebreaker
is that the two readings produce different data, not different code style.

Nothing sets `is_active = false` anywhere today: AC-022 landed as schema in
T-0004 and no code writes it yet. So this is unreachable in production right
now, and becomes reachable the moment termination is implemented — by which time
the derivation will have been running nightly for a while.

## What the tests found that I had not anticipated

**The unknown-store case is unreachable through the derivation.**
`test_unknown_store_fails_loudly` was supposed to stage a punch for a store that
does not exist. It cannot: `stg_timeclock.restaurant_number` carries its own
foreign key to `ref_stores`, so the bad row cannot be staged in the first place.
§6's edge row — "Assignment for an unknown store — FK rejects; derivation fails
loudly" — is satisfied one layer earlier than it reads. The test now asserts the
guarantee at both layers instead of pretending to exercise a path that does not
exist.

**Testing transactionality needed an injected failure.** Same cause: the
database will not accept a genuinely bad input, so there is no natural way to
kill a run halfway. `derive_display_name` is monkeypatched to raise on the
second person, which leaves the first person and assignment already written
when the run dies — exactly the state a non-transactional implementation would
commit. The test asserts the injection landed (`calls["n"] == 2`) as well as
asserting the rollback, because an injection that fired too early would make the
test pass for the wrong reason.

**My own teardown was broken, and passed anyway.** `_wipe()` deleted persons
matching `display_name LIKE '%t0006:%'`. But these persons are created *by* the
derivation, so their display names are whatever `derive_display_name` produced —
"Bir Singh" — carrying no marker at all. The filter matched nothing, persons
accumulated across tests, and the next test found them through the
`(clerk_id, normalized_name)` index and reported `persons_created == 0`.

Every test passed in isolation and eleven failed as a suite. A teardown that
silently deletes nothing is worse than no teardown, because the suite still goes
green whenever you look at one test. Persons are now found through their
assignments, which is the only handle that actually points at them.

**A determinism gap in my own SQL, surfaced by a primary key.** `stg_timeclock`
is keyed on `(restaurant_number, clerk_id, clock_in)`, so two punches for one
person on one day need different clock-in times. Fixing the test fixture made me
look at the query, where `DISTINCT ON ... ORDER BY business_date DESC` leaves
two same-day punches **tied** — and "the most recently seen `employee_name`"
would then be whatever the planner returned. The ordering now includes
`clock_in DESC`. AC-001 was always satisfiable only if that tiebreak existed;
nothing in the spec named it, and nothing would have caught it.

## Choices worth reviewing

**One transaction for the whole run.** `get_session()` wraps everything, so a
crash cannot leave a `ref_employees` row with no assignment — a person nobody
can reach and nothing will ever clean up. The cost is that a single bad row
fails the entire nightly run rather than 398 of 399 succeeding. That is the
right trade at this size and worth revisiting if the roster ever gets large.

**Existing assignments are loaded once, not queried per pair.** 399 pairs
against a few hundred assignments is a join, not a loop. Two dicts come out of
it: one keyed by `(store_number, clerk_id)` for "have I seen this", one by
`(clerk_id, normalized_name)` for AC-005's link. The second is updated as
persons are created, so two new assignments in the *same run* sharing an
identity land on one person — which `test_same_pin_same_name_two_stores_is_one_person`
covers and which a naive implementation querying only pre-existing rows would
get wrong.

**`INSERT ... RETURNING`, not `upsert_rows`.** PLAN §6 called this out and the
task forbids the alternative: `ref_employees` has no natural key by design,
because no field or combination identifies a human in this data. There is
nothing to upsert on.

**`incomplete_opened` is always 0.** CON-001 names the field; AC-018/AC-019 and
the completeness sweep belong to T-0009, and this task's FORBIDDEN_ACTIONS say
so. The field is present and documented as T-0009's to fill rather than left to
look like an oversight.

## What surprised me

That the most valuable thing the test suite did was fail *as a suite* while
every test passed alone. Three of this session's earlier findings were the
opposite shape — tests that passed and could not have failed, because they
established the happy precondition before exercising the branch. This one was a
test file that could only pass in isolation. Both are the same underlying
question: what would this test do if the thing it checks were broken.

Also: two of the eight ACs turned out to be about layers below this module.
AC-024 needs a decision about what a column means, and the unknown-store
precondition is enforced by a foreign key three tables away. Roughly a quarter
of the acceptance criteria for "the heart of the spec" were not about the
derivation logic at all.

# Resume — 2026-08-18, after B-0037 → A (D-041)

## AC-024, and proving the test earns its place

Reactivation is one guarded statement over everyone who clocked in this run:

```sql
UPDATE ref_employees
   SET is_active = true, termination_date = NULL
 WHERE employee_id = ANY(:employee_ids)
   AND (is_active = false OR termination_date IS NOT NULL)
```

One statement rather than a check per person, and the `WHERE` guard means the
common path — nobody terminated — writes nothing at all. Both branch points feed
the set: the person on an existing assignment, and the person reached through
AC-005's `(clerk_id, normalized_name)` link from a *new* assignment. The second
is the one worth naming, because someone who left store A and reappears at store
B under the same PIN never touches the existing-assignment branch.

The task's RESUME block told me to write the test so the two candidate answers
differ, and I did more than assert that this time — I checked it. With
`termination_date = NULL` removed from the UPDATE (option B of B-0037), the test
fails; restored, it passes:

```
option B (is_active only) : FAILED test_terminated_person_clocking_in_is_reactivated
option A (as decided)     : passed
```

That took thirty seconds and it is the difference between a test that covers
AC-024 and a test that merely mentions it. Three findings this session came from
tests that could not have failed; one deliberate check is cheaper than a fourth.

Four tests in total, because AC-024 has more edges than it reads:

- the same row reactivated, person count unchanged, `termination_date` cleared;
- the same, reached through the linking rule from a new store;
- an *active* person's row is not rewritten at all (the guard);
- a terminated person who did **not** clock in stays terminated — otherwise a
  nightly job quietly un-terminates the whole roster, which is the failure mode
  a naive "reactivate everyone we resolved" implementation would have.

## The serious thing I found in my own branch

Rebasing the halted branch onto `main` showed `src/subway_ops/dashboard/app.py`
modified. I had not touched it. Looking properly: **57 files across the repo**
were in my WIP commit — the whole of `src/` and `tests/`, reformatted.

The cause was two ordinary commands: I ran `uv run ruff format src/ tests/`
while chasing a lint finding, which reflowed the entire tree, and then
`git add -A` swept all of it into the commit. Neither command is wrong on its
own. Together they put a repo-wide reformat inside a task branch.

This is bad in a specific way rather than a general one. **T-0012 exists to do
exactly this reformat, once, in a commit of its own** — that is D-027, and its
whole value is that `git diff -w` can prove the commit changed nothing but
whitespace. Merging T-0006 with 57 reformatted files would have destroyed that
property permanently: the reformat would be spread across an unrelated feature
branch, unreviewable, and T-0012 would have nothing left to do and no way to
show it was safe.

I rebuilt the branch rather than trying to unpick it: tagged the contaminated
commit as `wip/T-0006-contaminated`, branched fresh from `main`, and checked out
only the four licensed paths. The branch now diffs against `main` at exactly
`derive.py`, `people/__init__.py`, `test_people_derive.py` and this journal.

**This is B-0031 again, and B-0031's option D is exactly what would have caught
it.** That option — teach the gate to assert the diff touches only DELIVERABLES
plus the ON_COMPLETION paths — was declined, and D-033 records it as a
"known-uncovered case rather than a surprise". It is no longer hypothetical: the
same class of escape has now happened twice, in different ways, three tasks
apart. The first was one symlink; this was 57 files. I am not reopening a
decided item, and the record already carries the reopen condition — but the
second occurrence deserves to be written down where whoever revisits D-033 will
find it.

Worth being precise about what saved it: not the gate, and not me noticing.
The **rebase** surfaced it, because a file I had never edited appeared in a
conflict listing. On a branch that rebased cleanly it would have gone through.

## What surprised me, second time round

That the resume was the easy part. B-0037 took a paragraph of code and four
tests; the contamination took longer to diagnose and fix than the entire feature
it was attached to. The halt worked exactly as designed — one question, one
answer, a few lines — and the incident had nothing to do with the domain at all.

Also worth noting for the ledger: seven of this task's eight ACs were built

dramatically cheaper than deciding it and being corrected. That is the first

# Rework — 2026-08-18, after the audit (D-042, D-043, D-044)

## The thing I did twice

The audit found that this suite had run the real derivation against production —
405 assignments, 342 persons, 13 real stores — because 25 of its 27 call sites
passed no arguments and `since=None` means "all of `stg_timeclock`". Those rows
were deleted on founder instruction.

Then the task file told me to re-run the tests on the clean database first, to
watch the false green collapse. I did. It collapsed exactly as predicted —
`test_new_pair_creates_assignment` failed because `DeriveResult` counts globally
and the answer was 406, not 1 — **and the run rewrote all 405 rows.** I deleted
them, ran the unscoped suite once, and put them straight back.

That is not a subtle failure. I knew what the defect was, I had just watched
someone else describe it precisely, I had the fix specified in front of me, and
I ran the unscoped suite anyway because the instruction said "run it first" and
I followed the instruction without thinking about what running it would do. The
instruction was right — seeing the failure is the proof the scoping matters —
but the correct order was to scope the calls first and then demonstrate the old
behaviour deliberately, on one test, rather than by executing the whole suite
against production.

Deleted again, with a second snapshot taken first. Both snapshots are in the
scratchpad. The final state is 0 assignments, 0 persons, `stg_timeclock`
untouched at 19,339 rows.

## What changed

**D-042 — `stores`.** `CON-001` now takes `stores: list[str] | None`. The
`WHERE` clause is two lines; the interesting part is the test file, where a
single `STORES` constant is passed at all 27 call sites. The parameter is not
the fix on its own — a default that means "everything" is still there for the
nightly run, which is correct. The fix is that a caller can now *say* what it
meant, and the suite says it once, in one place, where a reviewer can see it.

**D-043 — two passes.** Pass one applies every AC-004 rename. The identity index
is then rebuilt from the table, inside the same transaction. Pass two resolves
the pairs that had no assignment.

I rebuilt the index by re-reading rather than maintaining it incrementally as
renames landed. Incremental bookkeeping would have been one line and would
probably have been right; re-reading is obviously right, and this is the index
that decides whether two humans are one person. The `ORDER BY assignment_id`
matters for the same reason — `setdefault` over an unordered read meant the
person a link resolved to depended on the planner.

**D-044 — names.** Blank names are filtered before `DISTINCT ON` picks a winner,
so one nameless punch cannot erase a name the pair has already shown. A pair
that has never had a name is collected by a second query and gets
`Clerk <id> (unnamed)`. The empty-key carve-out in the index is gone, so AC-005
now holds uniformly instead of quietly not applying to nameless pairs.

## Proving the tests discriminate

Both new tests were checked against the behaviour they replace, not just
asserted to cover it:

```
D-043  index built before the renames (run-start snapshot) : FAILED
       two passes, as decided                              : passed

D-042  `stores` ignored inside derive_roster               : FAILED
       `stores` honoured                                   : passed
```

The D-042 check is itself instructive: ignoring the parameter made the test
create several hundred real-store assignments, which is the defect reproducing
itself under laboratory conditions. I cleaned those rows afterwards.

## A second contaminated test the audit did not catch

`test_unknown_store_fails_loudly` inserted an assignment using
`SELECT MIN(employee_id) FROM ref_employees`. On the clean database that is
NULL, and the test failed for the wrong reason — it had been passing only
because the production roster happened to be sitting in the table.

So the contamination had reached two tests, not one, and only the first was
visible in the audit's analysis. It is now self-contained: it derives its own
person from a synthetic punch. Worth noting that this one would have kept
passing indefinitely on any machine where the roster had been derived once.

## What surprised me

How much of "the tests pass" was load-bearing on ambient state. Nineteen tests,
two of which were reading rows that no test had created and no fixture had
declared. The suite never said "given a roster exists" — it just quietly
required one.

The general shape, which is the third instance this session after D-036 and
D-038: a test that does not construct the state it depends on cannot tell you
whether the code produces that state. Twice that was a precondition established
too early; here it was a precondition nobody established at all.

Also: `stg_timeclock` has 19,339 rows and a foreign key to `ref_stores`, so
every one of them is a real store. There was never a way to run this suite
against production data "a little bit". It was all or nothing, and the default
argument chose all.
