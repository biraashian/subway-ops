# T-0010 — Schema drift becomes declared rather than merely detected

Date: 2026-08-13
Branch: `forge/T-0010`
Type: bug_fix
Anchors: D-024 (from B-0022) — harness maintenance, no spec
Decisions: none new; implements D-024

## What was built

Two pure functions in `scripts/schema_snapshot.py` — `parse_declaration` and
`compare_declaration` — plus an `--expected` mode on `--diff`, the matching
wiring in `scripts/verify.sh`, `.drift/expected/README.md`, and 15 tests.

A task that will see schema drift now writes `.drift/expected/T-####.txt`. The
gate compares observed drift to the declaration and passes only on an exact
match. With no declaration present, behaviour is unchanged from before: any
drift fails.

## The bug this fixes

I wrote the drift check in T-0000 to exit 1 on any difference. That is correct
for a check that only ever guards against *accidental* schema change, and wrong
the moment a task's whole purpose is a migration. T-0003 — the first task that
touched one — halted on it. T-0004 would have, and so would every migration
after.

The check already knew. It printed "Schema drift is not automatically wrong — a
migration is supposed to change the schema. It must be INTENDED", told the
reader to confirm against the journal, and then had no way to record that
anyone had. It described the right process and enforced a different one.

## Why a declaration, and why a stale one must also fail

B-0022 offered three ways out. Tracing drift to migrations on the branch was
rejected because it cannot see an `ALTER` a migration makes by accident — which
is the single case most worth catching, since a hand-written `ALTER TABLE` in an
otherwise innocuous migration is exactly how a column quietly changes meaning.
Demoting drift to a warning was rejected because it removes the review surface
at the one moment review actually happens.

The declaration keeps the property that made the check worth writing: a person
looks at the schema change. It just lets the looking happen once, in the task,
instead of blocking forever.

**A stale declaration fails too, and that is the part worth defending.** A line
declared but no longer observed means the file has drifted from reality — and a
file that reads as "someone checked this" while being wrong is worse than no
file. It is the same failure mode as `SUBWAY_OPS_TASKS.md` marking a backfill
complete that had never run: documentation asserting a verification that did not
happen. So `compare_declaration` returns both directions and either one reds.

## The thing I got wrong, found by running it

T-0010 changes no schema at all. Its deliverables are two scripts, a README and
a test file. I expected its own pre-merge to show no drift.

It showed one line: `+ table ops_worklist_items (10 columns)` — **T-0003's**
table.

The reason is structural rather than accidental. Drift is measured against
`.drift/schema-before.json`, which rotates at the **post-merge** of the previous
task. T-0003 applied migration `020` to the shared database during its build,
then halted before merging. So its table is live, the baseline predates it, and
every subsequent task sees it as drift until T-0003 merges.

That broke my own definition. `.drift/expected/README.md` originally said "a
task that intends to change the schema declares the change here" — and under
that reading there was nothing honest for T-0010 to write. Declaring a line it
did not cause would put a false claim in the artifact designed to prevent false
claims.

**So I changed the definition rather than the declaration.** The file now
asserts:

> Every schema difference between the baseline and the live database is
> accounted for, and here is what each one is.

Not "this task caused these". Under the accounting reading there *is* an honest
thing to write: declare the line, attribute it in a comment. `T-0010.txt` opens
by stating in full that this task changes no schema and that the line belongs to
T-0003, with the reason the baseline has not caught up.

I am fairly sure this is the better semantics and not a rationalisation, for one
concrete reason: the accounting reading is the one that still catches the case
the gate exists for. An unexplained table appearing in the database fails
whether or not this task caused it — and "a table appeared and nobody knows
whose it is" is *more* alarming than "this task added a table", not less.

It is also a symptom of B-0001 / D-025. With no test database, a build applies
its migrations to production. Once tests run against a container, most of this
class of cross-task drift stops existing.

## Verification

Every path exercised against the live schema, not only fixtures:

| Case | Exit | Wanted |
|---|---|---|
| matching declaration | 0 | 0 |
| undeclared drift | 1 | 1 |
| stale declaration | 1 | 1 |
| declaration named but missing | 1 | 1 |
| no declaration, drift present | 1 | 1 (original protection) |

That last row is the one I most wanted to see. The whole risk of this change is
loosening a gate; the test that matters is that the gate still fails when nobody
declares anything.

15 unit tests, all pure — no database. A gate whose own tests need the thing it
guards is a gate people stop running, and these execute in 0.27s.

`test_failure_output_names_the_undeclared_lines` asserts on the *content* of the
failure, not just the exit code. The original check's "1 change(s)" was true and
useless; a reader needs the undeclared lines and the stale lines named
separately, because they mean opposite things and have opposite fixes.

## What I deliberately did not touch

`scripts/verify.sh` got exactly one edit — the drift block — plus the headline
extractor for the new messages, which would otherwise have rendered a declared
pass as a bare "1 change(s)" and read like a failure in the results table.

I did not write `.drift/expected/T-0003.txt`. T-0003 declares its own drift when
it resumes; writing it here would be me marking another task's homework.

## What surprised me

That the fix's first real run immediately produced a case its own documentation
could not describe. I had reasoned about declared drift entirely in terms of one
task changing one schema, and the very first execution — on a task that changes
nothing — broke that frame.

Worth remembering as an argument for running things before believing them. The
15 fixture tests all passed on a definition that was wrong.
