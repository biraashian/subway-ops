## Why `normalize_name` does so little

It lowercases, strips, and collapses whitespace. That is the whole function, and
the restraint is the design.

B-0014 measured what the data actually looks like: 250 distinct clerk_ids across
399 `(clerk_id, store)` pairs, 56 clerk_ids carrying more than one name, PIN `8`
appearing under five different names at five stores. The decision was option B —
link on exact `clerk_id` plus exact normalized name, everything else stays
separate and office merges it.

So the normalizer's job is to remove the three differences that are *always*
noise — case, surrounding space, doubled internal space — and to remove nothing
else. It does not strip punctuation. It does not drop middle names. It does not
reorder tokens. Every one of those would be a small step toward fuzzy matching,
and the task's third FORBIDDEN_ACTION forbids even leaving a fuzzy matcher lying
around unused, on the grounds that someone wires it in later.

The asymmetry is worth restating because it is the entire argument and it is
easy to forget when you are looking at `singh, bir` and `bir` and knowing
perfectly well they are the same person: under-linking produces two rows that
office merges in seconds, with the merge recorded in
`ops_employee_identity_log`. Over-linking silently fuses two people's hours,
wages and certificates, and *nothing downstream ever detects it*. There is no
alarm for "these two humans became one." I wrote a test that asserts
`normalize_name("singh, bir") != normalize_name("bir")` — a test that the system
does **not** do the clever thing, on data where the clever thing happens to be
right.

## Two readings I took from the AC text rather than inventing

Both are places where I could have made a call and instead went back to what the
ACs actually say. Recording them because the audit should check my reading, not
just my code.

**1. "Of the form `LAST, FIRST`" means exactly one comma.** AC-026 governs that
form; AC-027 governs everything else. `smith, john, jr` has two commas and is
therefore not that form, so it returns verbatim. The alternative — split on the
first comma and treat `john, jr` as the given name — requires deciding which
comma separates the surname, and the ACs do not say. Under my reading nothing is
dropped, no guess is made, and the string lands on office's desk to correct,
which is precisely the escape hatch AC-028 exists to provide. Same reasoning
covers `singh,` and `, bir`: one comma, but only one name, and a display name
with a dangling space is not a name.

**2. Verbatim includes the case.** `bir` stays `bir`, lowercase. The task's own
test name says so ("`bir` stays `bir`") and AC-027 says "use it verbatim". I
wanted to title-case it — it looks unfinished — and that instinct is the bug: a
helpfully-capitalized value is a *derived* value wearing the costume of an
*observed* one, and the whole point of `display_name_is_manual` and the
observed/normalized split is that the system can always tell those apart.

## The capitalization I deliberately left wrong

On the parse path, each whitespace-separated token gets its first character
upper-cased and the rest lower-cased. `singh, bir` → `Bir Singh`. `REDWAN, SHAH`
→ `Shah Redwan`. Good.

`o'brien, pat` → `Pat O'brien`. `mcdonald, sean` → `Sean Mcdonald`. Both wrong.

I left them wrong and wrote a parametrised test that pins both wrong answers.
That looks perverse written down, so: any rule clever enough to fix `O'Brien` and
`McDonald` is clever enough to mangle a name it has never seen, and this is a
250-person roster spanning several naming traditions. B-0018 already decided the
repair path — office types the right thing once, and AC-028 guarantees no later
derivation run overwrites it. A predictably-wrong name a human can fix
permanently beats a heuristic nobody can predict.

Pinning them in a test means the next person to change this has to change a test
that says, in its docstring, why it was left this way. If they still change it,
they meant to.

## `effective_role` raises twice, and both are the interesting part

The function is four lines of logic. The design is in the two `ValueError`s.

**Empty raises rather than returning `crew`.** A person with no active
assignment has no role. Returning the lowest rung would be a real answer,
indistinguishable from a real answer, and the caller would carry on and grant
crew-level access to somebody the system knows nothing about. An exception at
least stops.

**Unknown raises rather than being skipped.** A role off the ladder is either a
typo or a ladder change that has not reached `ROLE_ORDER`. Skipping it means
resolving a person's authority from whichever of their roles happened to be
spelled correctly, which is the kind of bug that works fine for a year.

`ValueError` because CON-003 already uses `ValueError` for an out-of-contract
argument (a non-positive rate), so this matches the spec's own house style
rather than introducing a second convention.

## The ordering test is the most important test in this task

`test_role_order_matches_codex_ladder` asserts the literal tuple, element by
element, rather than checking membership or checking that "the highest one
wins".

That is on purpose. Index position **is** authority in this module — everything
compares by `ROLE_ORDER.index` — so swapping two entries is a permission change
that compiles cleanly, passes every behavioural test in the file, and escalates
crew above office. A set comparison would not catch it. A test that only checks
`effective_role(["crew", "owner"]) == "owner"` would not catch it either, as
long as the swap happened somewhere in the middle.

The task's NOTES called this out and they were right to.

Not "26 tests pass". Each AC checked on its own:

- **AC-029** (highest among active assignments) — 5 tests: the highest wins,

  `effective_role`'s docstring with the concrete failure named (a shift lead at

## The worktree was quietly running a weaker gate

Worth its own section, because I nearly shipped a false claim on the strength of
it and because it will bite the next `[P]` task identically.

`.env` is gitignored, so `git worktree add` does not bring it. `DATABASE_URL` was
therefore unset inside the worktree, and every DB-backed test in the repo
**skipped**. The adhoc sweep still printed `✅ All checks passed`. I read that as
green and wrote "545 passed" into this journal from memory of what the main repo
reports.

The real numbers, before and after symlinking `.env` into the worktree:

```
worktree, no .env :  465 passed, 109 skipped
main repo         :  545 passed,   6 skipped
```

103 tests — T-0003's 14, T-0004's 21, and every DB-backed test that predates
Burst — were not running. Nothing about that was visible in the adhoc summary.

**Pre-merge caught it and adhoc did not.** The schema snapshot step fails hard
with "a drift check that passes without reading a database has verified
nothing", which is exactly the right behaviour and is why this is a story about
a near miss rather than a defect that shipped. But the inner loop is where a
build actually lives, and for the whole of this build the inner loop was
asserting substantially less than I believed. A skip is not a pass, and 109 of
them summarised as a green tick is the same "silent skip is a vacuous pass"
failure T-0000 closed in `verify.sh` for a missing codex gate.

Raised as **B-0030**, non-blocking: adhoc should assert `DATABASE_URL` the way
pre-merge does, or at minimum report the skip count in its summary line.

The fix for this task was one symlink. Recording it because "run `[P]` tasks in
a worktree" is now written policy, and the policy is incomplete without it.

## What surprised me

That the two "vocabularies of six roles" problem from T-0004 followed me here,
and that the right move was a test rather than a comment.

`ROLE_ORDER` is codex 06's job ladder: crew, shift_lead, store_manager,
field_manager, office, owner. `ref_users.role` after migration 021 is a
different six: it carries `readonly` and has no `shift_lead`, because it is an
*access* vocabulary rather than a job one. Two sets, same size, differing by two
elements, sitting one package apart — a genuinely good way to lose an afternoon
later.

So `test_effective_role_rejects_a_ref_users_only_role` feeds `readonly` to
`effective_role` and asserts it raises. The divergence is now enforced rather
than described: if someone ever merges the two vocabularies, that test fails and
they have to look at why the split existed. In T-0004 I could only write a
comment about this, because a migration cannot assert anything about another
table's constraint. Here I could write the assertion. The comment was the best
available then; the test is better, and the difference is worth noticing.

Second surprise, smaller: the ruff `RUF007` and `RUF043` findings both improved
the code rather than just satisfying the linter. `RUF043` pushed me off a regex
alternation in T-0004 and onto the exact constraint name, which is a stricter
test. `RUF007` pushed `zip(x, x[1:])` to `itertools.pairwise`, which says what it
means. I have been treating the lint step as a tax and it has now twice been a
review.

# Rework — 2026-08-17, after the /audit RED (B-0031 → D-033)

The audit was right and the finding was mine. This section records the fix and,
more usefully, why I made the mistake, because the mechanism that produced it is
still there for the next person.

## What the defect actually was

`forge/T-0005` committed a sixth path its DELIVERABLES never licensed:

```
120000  tests/fixtures/recorded -> ../../../../../tests/fixtures/recorded
```

That relative target resolves only from inside
`.claude/worktrees/T-0005/tests/fixtures/`. Five levels above `main`'s own
`tests/fixtures/` is the filesystem root, so on `main` it points at
`/tests/fixtures/recorded`, which does not exist. The 15 recorded fixtures are
gitignored, so git's index cannot see them, nothing conflicts, and the merge
**replaces a real directory with a dangling link and exits 0**.

I had written B-0030 the same afternoon, about exactly this failure shape — a
skip presented as a pass. Then I took the workaround B-0030 describes and
promoted it from a worktree-local annoyance into a permanent property of `main`.
Writing down a failure mode is not the same as recognising it in your own next
action.

## Why I committed it, which is the part worth keeping

Not carelessness, and that is what makes it worth recording. Pre-merge Run 1
failed on `git status: NOT CLEAN — 3 path(s) modified or untracked`. The symlink
was one of the three. The shortest path from a red `git status` to a green one is
`git add`, and I took it without asking whether the file belonged in the commit
at all.

The gate enforces worktree **cleanliness**. It does not enforce deliverable
**scope**. Those feel like the same check when you are staring at a red status
line, and they are not: cleanliness says "nothing is lying around", scope says
"only these paths may change". Every future `[P]` task will hit the same red
status for the same reason and be offered the same shortcut.

D-033 removes the temptation rather than trusting me not to take it: the ignore
rule loses its trailing slash, so the symlink is invisible to `git status` and
there is nothing to `git add`. B-0031's option D — teaching the gate an actual
scope check — was considered and **not adopted**, so this class stays uncovered
by design, and the decision says so in as many words.

## The fix, both halves

**B — the ignore rule.** `.gitignore:41` was `tests/fixtures/recorded/`. A
trailing slash matches a directory and not a symlink, which is precisely why the
link showed up as untracked rather than ignored. Dropping one character makes the
rule cover both.

**A — untrack the link.** `git rm --cached tests/fixtures/recorded`. It leaves
the file on disk, so this worktree keeps working, while removing it from the
branch.

Three properties, each checked rather than assumed:

```
link on disk and resolving  :  lrwxr-xr-x  ->  ../../../../../tests/fixtures/recorded  (15 files)
ignored by the new rule     :  .gitignore:41  tests/fixtures/recorded
git status                  :  M .gitignore  ·  D tests/fixtures/recorded   (nothing untracked)
```

## I ran the proof too early and it failed

The audit demonstrated the defect by merging the branch into a throwaway clone of
`main` that had a real fixtures directory. I reran that exact procedure to
demonstrate the fix, and it came back:

```
merge exit = 0
tests/fixtures/recorded -> ../../../../../tests/fixtures/recorded   (dangling)
sample.json: No such file or directory     ← GONE
```

The fix had not failed. I had fetched `forge/T-0005`, and my changes were staged
but not yet committed, so the branch still carried the symlink. The proof was
correct and the thing I pointed it at was stale.

Recording it because the near-miss is instructive in both directions: had the
result come back green for an equally accidental reason, I would have written
"verified" in this journal and been wrong. A verification you did not watch fail
first is a verification you have not really calibrated. The re-run after
committing is in the next section, and it is the one that counts.

## The merge is now safe, proven the same way

Same throwaway clone, same real fixture present, branch this time carrying the
fix — see the transcript recorded below the pre-merge run.

## What I would tell the next `[P]` builder

1. A worktree gets tracked files and nothing else. Whatever gitignored artifact
   the suite needs is absent, and the inner loop will not tell you. T-0014 makes
   setup do this for you; until it lands, do it by hand and do **not** commit
   the result.
2. When `git status` goes red at pre-merge, read the list before staging any of
   it. The check is asking "is anything lying around", and the right answer is
   sometimes "yes, and it should stay lying around".
