# T-0007 — Wages: effective-dated rates, permission guard, weekly cost with overtime

Date: 2026-08-17
Branch: `forge/T-0007`
Type: mart
Anchors: SPEC-PPL-001 · REQ-003 · AC-011…AC-017 · CON-002, CON-003, CON-005
Decisions: none

## What was built

Two modules and 37 tests. `people/wages.py` records and resolves rates;
`people/cost.py` turns hours and a rate into a weekly dollar figure, or refuses
to. Two constants in `config.py`, four new exports on the package.

This is the task that closes the NULL in `mart_store_weekly.labor_cost_pct`
which has stood since the column was written — except it does not, quite. It
produces `cost_week`; wiring that into the mart is a later task in another spec.
Worth saying plainly because "wages land" sounds like the labor-cost number
starts working, and it does not yet.

## The one function holding INV-005 up

`record_wage` is, on its own, the entire enforcement of "a wage is never updated
in place". That is not an overstatement of a code comment — it is the finding
the T-0004 audit carried forward into this task's NOTES, and I want it recorded
again here from the implementer's side.

`PRIMARY KEY (employee_id, effective_date)` refuses a *second row* for a date
that already has one. It says nothing whatsoever about mutating the row already
sitting there. The audit proved it: a raw `UPDATE ref_employee_wages SET
hourly_rate = 99` succeeds against the live table and rewrites pay history with
no error and no trace beyond `set_at` staying stale.

So `record_wage` has no update path, no `ON CONFLICT DO UPDATE`, and no `force`
parameter. A correction is a new row on a new effective date. Re-recording an
existing date raises.

The test for this deliberately asserts more than "an error was raised":

```python
with pytest.raises(Exception, match="ref_employee_wages_pkey"):
    record_wage(..., hourly_rate=Decimal("99.0000"), ...)
assert rate_in_force(person, today) == Decimal("18.0000")
```

The second line is the one that matters. An exception that still left the row
mutated would pass a raises-only test and fail the invariant. What INV-005
protects is that a report already sent out can be reproduced next month, and
that property is only true if the *old value survives*.

## Ordering the two guards, which turned out to be a real decision

`record_wage` checks `actor_role` before it validates `hourly_rate`. That
ordering is deliberate and I nearly wrote it the other way round, because
validating cheap arguments first is the usual habit.

If the rate were validated first, an unauthorised caller passing a negative rate
would get `ValueError` and a caller passing a valid rate would get
`PermissionError`. That difference is a small oracle: it tells someone who may
not set wages whether their proposed rate would have been accepted. Tiny, but
free to avoid, and there is a test pinning it —
`test_permission_is_checked_before_the_rate` passes a negative rate as a
non-office role and asserts `PermissionError`, not `ValueError`.

## AC-013's second clause is about the exception message

"SHALL NOT include the rate in any response body." An exception message *is* a
response body — the moment it reaches a log line, a Sentry event or an API error
handler, it has been published. So the `PermissionError` names the role and the
employee id and never the rate.

`test_permission_error_body_contains_no_rate` checks `repr` and `str` of the
raised exception for the digits, using a distinctive rate (`47.1234`) so a
partial leak would show. It asserts on `"47"` as well as the full value, so a
truncated or reformatted rate cannot slip through.

## The overtime arithmetic is pure, and that was the task's own instruction

The NOTES said to factor the split as a pure function of (hours, rate) so the
boundary tests need no database, and that was good advice. `split_weekly_hours`
and `cost_hours` are importable and testable with nothing running; the six
boundary cases run in microseconds.

The boundary itself: **40.00 exactly is all regular.** AC-016 says "beyond 40",
and 40 is not beyond 40. A `>=` in place of `>` would pay a premium on an hour
nobody is owed one for, across 250 people, every week, forever, and no test that
only checked "50 hours produces overtime" would ever notice. `40.01` produces
exactly one cent of premium hours.

The other half is that the split happens on the person's **summed** weekly
hours, never per shift and never per store. Someone at 25 hours in each of two
stores is at 50 hours and owed 10 hours of premium, and no store-scoped view
would ever produce that number — which is exactly why `split_weekly_hours` takes
a single total rather than a list of shifts. The signature makes the wrong
version awkward to write. There is a DB-backed test for it across two real
stores.

`cost_week` returns a per-person figure and does not allocate the premium across
stores. That is B-0020/Q-007, fenced out by NG-007, and it belongs to the
labor-dollar mart.

## I chose not to round, and that is a choice

`hourly_rate` is `NUMERIC(12,4)`; hours carry their own scale; the product can
land past four decimal places. Nothing in SPEC-PPL-001 or codex 02 names a
rounding mode.

So `cost_hours` returns the exact `Decimal` and quantizes nothing. Picking
`ROUND_HALF_UP` and a scale would have been inventing a money rule — a small,
extremely reasonable-looking invention of precisely the kind Rule 1 exists to
stop, and precisely the kind B-0026 caught in T-0003. Exactness is also the
safer default independent of the rule: rounding once at the edge beats rounding
at every intermediate step.

`test_arithmetic_is_exact_and_unrounded` pins it against a rate that does not
land on a cent, so a future quantize would fail a test that explains why.

## Two ways a week refuses to be costed, and neither returns zero

CON-005 is explicit, and I am glad I read it before writing, because AC-017 read
on its own points somewhere slightly different.

AC-017 says a NULL-hours shift is "uncosted" and the containing aggregate is
marked `partially_costed`. Read alone, "partially costed" suggests the other
shifts still produce dollars. CON-005 settles it: `is_costed = False` when the
rate is absent **or any shift's `hours_after_adj` is NULL`; `dollars` is then
`None`, never zero.

Having implemented it, the contract is right and my first reading was wrong. If
one shift's hours are unknown, the person's weekly *total* is unknown — and
therefore so is whether they crossed 40. A partial figure would be confidently
wrong in the one place overtime is decided, which is worse than abstaining.

Both refusals return `dollars=None`, never `Decimal("0")`. INV-007 and INV-008
are the same idea from two directions: "we do not know what this person is paid"
and "this person is paid nothing" are different facts, and a zero flows into a
labor-cost mart and understates it invisibly with nothing to alarm on.

The hours that *were* observed are still returned and still split, so an
hours-based metric keeps working while the dollar figure abstains — AC-021
requires exactly that.

## INV-006 is not enforced on the read path, and I did not add it

INV-006 says "a wage rate is readable only by `office` and `owner`". `AC-013`
says a caller whose role is not office or owner who "requests a wage" is refused.

`record_wage` takes `actor_role` and enforces it. **`rate_in_force` does not
take an actor role at all** — CON-002 specifies its signature exactly as
`rate_in_force(employee_id, on: date) -> Decimal | None`, and adding an
unspecified parameter is structure past the licensed shape, which is the finding
that made T-0003 red.

So as delivered, the guard is on the write and the read is unguarded at this
layer. I think that leaves INV-006 genuinely unenforced for reads: `cost_week`
calls `rate_in_force` internally, and any future view could too.

I did not bench it, because the contracts are unambiguous about what this task
ships and building to them is not a gap-fill. But it is the thing in this task I
would most want a second pair of eyes on, and it is in the founder note.

## AC verification, individually

- **AC-011** — 3 tests: insert works and carries `set_by`/`set_at`; a repeat on
  the same date is refused *and the original value survives*; a backdated
  correction leaves the later row intact and produces 2 rows, not 1 edited one.
- **AC-012** — 4 tests: the rate for a past date is that date's rate, not
  today's; before/on/after a raise, with "on" belonging to the new rate per
  REQ-003's "less than or equal"; `None` when nothing is in force; `None` for a
  date earlier than the first row. Plus a DB-backed costing test proving a later
  raise does not re-price an old week.
- **AC-013** — 4 tests: every rung below office refused (crew, shift_lead,
  store_manager, **field_manager** — the interesting one, since they outrank a
  store manager and run a territory and still may not touch pay); the refusal
  body carries no rate; the allow-list is exactly two; permission is checked
  before the rate.
- **AC-014** — 3 parametrised cases (0, -0.0001, -20) refused with `ValueError`
  and **nothing written** — the test asserts a row count of zero afterwards, not
  just that it raised.
- **AC-015** — a punch reading 8.00 before adjustment and 6.00 after costs 6
  hours. B-0016 chose `hours_after_adj` because the POS adjustment is already
  somebody's decision on 1,369 of 19,089 rows.
- **AC-016** — 6 boundary cases pure (0, 39.99, 40, 40.01, 50, 168), the 1.5
  multiplier, a total-preservation property, and the two-store summing case.
- **AC-017** — one NULL shift makes `dollars` None and `is_costed` False while
  the 30 observed hours are still reported.

Plus `test_shifts_outside_the_business_week_are_excluded`, which is not attached
to an AC but guards codex 01: a punch the day before the week starts must not
count. That is what `timedelta(days=7)` arithmetic gets wrong two days out of
every seven, and the FORBIDDEN_ACTIONS call it out.

## What surprised me

That `test_a_week_with_no_shifts_costs_zero_when_a_rate_exists` is the odd one
out and needed thinking about. Every other path treats "zero" as a dangerous
answer, and this one returns `Decimal("0")` with `is_costed=True` on purpose:
somebody who worked no hours and *has* a known rate cost nothing, and that is a
fact rather than an absence. The distinction the whole module is built around is
unknown-versus-zero, and this is the one case where zero is the truth.

Second, smaller: ruff's lint pass improved the code again rather than just
satisfying itself. `SIM300` caught three Yoda conditions I had written without
noticing, and `RUF043` pushed a `match=` pattern to a raw string — the third
time this session the lint step has functioned as a review rather than a tax.

# Rework — 2026-08-17, after the audit went RED (B-0032 → A, B-0033 → C)

Two findings, both mine, and they failed in different ways that are worth
separating because the lesson is not the same.

## B-0032 — the one I did not notice I was deciding

`cost_week` resolved one rate for the week and used `week_finish` to get it. I
wrote that line without registering that "which date represents a week" was a
question. AC-012 defines resolution for a *date*; nothing anywhere defined it
for a *week*. That is a Rule 1 gap and I filled it in passing.

The cost, measured by the audit against the live database: a raise effective
mid-week, 10h either side, returned **$600 against a correct $400** — every
pre-raise hour paid at the post-raise rate, a 50% overstatement, with
`is_costed=True` so it reads as authoritative. It feeds
`mart_store_weekly.labor_cost_pct`, the column this entire spec exists to
un-NULL.

**The part that stings is the test.** I wrote
`test_rate_is_resolved_for_the_week_not_today` and believed it covered this. It
records its wage *before* the week opens, so `week_start` and `week_finish`
resolve to the same rate and the choice under test cannot fail. A test can be
about the right subject, pass honestly, and still be incapable of detecting the
defect — because it never constructs the case where the two candidate answers
differ. I have started asking a different question of a test: not "does this
exercise the behaviour" but "which wrong implementations would survive it".

## B-0033 — the one I noticed and then decided anyway

AC-013 and INV-006 describe a *read*. CON-002 gives `rate_in_force` no actor.
So the spec required a guard the contract forbade the shape of.

I resolved that contradiction in **opposite directions in the same file** —
adding an unspecified `actor_role` to `record_wage` while declining to add one
to `rate_in_force` — noticed the inconsistency, wrote a paragraph about it in
this journal, and shipped. The audit is right that writing it down is not the
same as flagging it. Rule 1 has no confidence exemption, and the fact that I
could argue the position well is not evidence that it was mine to take.

D-037's answer is the two-accessor split I would probably have proposed if I had
benched it. That does not make shipping it the right call; it makes it a correct
guess, which the law is explicit is still a defect.

## What the rework actually changed

**`split_weekly_hours` is gone.** Under one rate per week it was enough to know
that 10 of 50 hours were overtime. Under per-shift pricing you have to know
*which* 10, so the function was replaced by `allocate_overtime`, which walks the
week in `clock_in` order and returns a (regular, overtime) pair per shift. The
40-hour line can now fall through the middle of a single shift, and a test pins
that.

I removed `split_weekly_hours` rather than leaving it. It had passing tests and
no production caller — the exact shape of code that survives three refactors
because deleting it feels like losing coverage. The named acceptance test
`test_overtime_split_at_boundaries` still exists and still expresses AC-016 in
weekly terms; it now goes through a small helper that sums the allocation.

**Which rate the premium multiplies needed no new decision.** I flagged it at
`/bench` as a sub-question needing an answer in the same sitting, and I was
wrong that it was open: Q-007 (B-0020) already defines the overtime hours as
"the hours after the 40th, wherever worked, ordered by `clock_in`". That
ordering identifies which shifts hold the premium hours; per-shift pricing then
prices them. Only Q-007's *ordering* is used — its attribution of the premium to
a store stays fenced out by NG-007, and `cost_week` still returns a per-person
figure.

Worth noticing that this is the second time this week the answer was already in
the record and I treated it as absent. The first was reading AC-017 alone and
nearly contradicting CON-005.

**A shift with no rate now makes the week uncosted**, where previously the check
was "no rate for the week". Someone hired mid-week has no rate for the days
before they were hired, and a partial figure would understate rather than
abstain. Same machinery, finer grain.

**`read_wage` (CON-006)** is the guarded human-facing read. `rate_in_force`
stays unguarded and internal — and that is now pinned by a test asserting its
signature has no `actor_role`, so anyone who later adds one is sent to D-037
rather than quietly merging the two accessors.

**`cost_week` stays unguarded and its side channel is documented, not hidden.**
Any caller with `dollars` and hours recovers the rate by division. D-037 accepts
this and scopes INV-006 to say what the library actually guarantees. Writing
"the rate is protected" over a function that hands it out by arithmetic would be
worse than saying plainly where the boundary is.

## The test assertion that actually failed the gate

`test_permission_error_body_contains_no_rate` asserted `"47" not in body` where
`body` also carries the `employee_id`. `employee_id` is `BIGSERIAL` and climbs
with every test run, so the test broke the moment that id happened to contain
`47`. The audit called it latent; by the time I re-ran the gate at `0a1e02e` it
was live, and it is what took that run to exit 1.

The assertion was broader than the property it was testing. It now checks the
formatted rate only, with a comment saying why the broad version was wrong —
because the tempting fix is to widen it further, and a test that fails on
unrelated data gets muted rather than fixed.

## What surprised me

That the gate caught the flake and the audit caught the defect, and neither
caught the other's. The gate cannot see that $600 is the wrong number; every
test passed and the sweep was green at `94eee8b`. The audit would not have
noticed a test that only fails on certain autoincrement values. Two independent
checks with genuinely different blind spots, and this task needed both.

Also: the rework is larger than the finding sounded. "Resolve the rate per
shift" reads like changing one argument. It replaced the costing query, deleted
a function, changed what "uncosted" tests for, and added a chronological
allocator — because pricing per shift means the *identity* of the overtime hours
starts to matter, and nothing before this had to know it.

# Rework 2 — 2026-08-17 (B-0034 → B, B-0035 → A)

Two narrow changes. Neither touched the per-shift pricing or the guarded read
from rework 1, which the audit re-probed by hand and confirmed.

## D-038 — an empty week has to ask

`cost_week` resolved rates only for the dates that carried shifts. With no
shifts it never consulted the wage table at all and fell through to the costed
branch, so a person with no wage row got `dollars=Decimal("0")`,
`is_costed=True` — and so did `employee_id 999999999`, which does not exist.

The $0 was arithmetically true. Zero hours cost zero at any rate. What was false
was `is_costed=True`, and that is the whole finding: the flag is the only
channel that distinguishes "we priced this" from "nothing contradicted us", and
it was quietly reporting the weaker thing.

The fix is one branch: no shifts ⇒ resolve at `week_finish` ⇒ absent means
uncosted. `week_finish` rather than "today" so a historical empty week stays
reproducible.

**This is the second instance of the same defect in one task**, and that is the
part worth recording. D-036 was an undefined case filled silently; so was this.
Both had a covering test that could not have caught it, for the identical reason
— the test establishes the happy precondition before exercising the branch, so
the two candidate answers never differ inside it. `test_rate_is_resolved_for_the_week_not_today`
recorded its wage before the week opened; `test_a_week_with_no_shifts_costs_zero_when_a_rate_exists`
recorded a wage before asking about the empty week.

So the new test is built the other way round. `test_empty_week_with_no_wage_row_is_not_costed`
sets up **nothing** — no wage, no punches — and asserts `dollars is None`. Under
the old behaviour it fails. `test_a_nonexistent_employee_is_not_costed` takes no
fixture at all, because the case that made the old answer indefensible was a
confident price for a person who is not in the database.

The question I now ask of a test is not "does this exercise the behaviour" but
"which wrong implementation survives it". Both of these were written from that
question.

## D-039 — the tests were writing to real stores

`tests/test_people_cost.py` pulled the two lowest store numbers out of
`ref_stores` — 10393 and 17967, both live — and inserted up to 35 hours of
`stg_timeclock` punches against them inside the current business week.

Teardown worked and left nothing behind; the audit verified that and so did I.
The exposure is the crash window: teardown is a fixture finalizer, and a killed
run leaves phantom punches on two real stores in the open week with no owner and
no alarm. codex 13 says "never point a test at a real store number" and it says
so because `test_mart_recon_weekly.py` spent three months hard-deleting a real
store's history on every run.

I read that convention before writing these tests. I took "no real store number"
to mean "no hardcoded store number" and looked one up instead, which satisfies
the letter of what I remembered and inverts the intent — the rule is about which
rows get written, not about where the literal appears in the source. Worth
recording precisely because it did not feel like a violation at the time.

The fixture now creates `T-PPL-1` and `T-PPL-2` with `is_active=false` and drops
them. `is_active=false` is not decoration: an active store is one the ingests
pick up, so it is what makes a crashed run harmless rather than merely tidy. The
test asserts both halves.

## What I did not do

The same pattern lives in T-0004's merged tests, which read real store numbers
to satisfy a foreign key. That writes nothing to staging and is far less
dangerous, but the convention has no read-only exemption. It is **T-0016**,
along with D-040's per-run namespacing, because both change the same files and
splitting them would only manufacture a merge conflict. I left it alone rather
than tidying it in passing.

## What surprised me

How much of this task's total cost was spent on things the code did correctly
from the first commit. The overtime boundary, the INV-005 insert-only guarantee,
`hours_after_adj`, the `Decimal` money path, the per-person weekly figure — none
of those ever moved. Four findings across two audits, and every one of them was
either an undefined case I filled or a convention I applied to the letter rather
than the purpose. Not one was a mistake about the domain.

That is a useful thing to know about my own failure modes: the risk is not
getting the arithmetic wrong, it is answering a question nobody asked me and not
noticing I answered it.
