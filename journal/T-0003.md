# T-0003 — ops_worklist_items and the generic worklist helper

Date: 2026-08-13

## What was built

The first product code under Burst. Three files: migration `020_worklist.sql`,
`src/subway_ops/db/worklist.py`, and `tests/test_worklist.py` (12 tests).

`ops_worklist_items` is codex 02's spine — the table every reconciliation
exception, expiry nudge, ungraded task and pending approval writes to, and the
one screen that answers "what needs a human today". Two functions:
`open_item(...) -> int | None` and `resolve_item(...) -> int`.

## Why this table lives here at all

It is referenced by AC-018 and AC-020 of a spec that does not own it —
SPEC-APP-001 was scoped to build the worklist, and SPEC-APP-001 has not been
written. PLAN §1 made the call: PPL creates it because PPL is the first
consumer, and codex 02 already defines the shape completely, so nothing is
being invented. SPEC-APP-001 builds the screen, not the table.

Putting the module in `db/` rather than `people/` is the same reasoning one
level down. Every later phase writes worklist items; if the helper lived under
`people/`, Phase B's reconcilers would import from Phase A's package for no
reason other than where the code happened to land first.

## The one thing I got wrong, and how

I first wrote `assigned_role TEXT NOT NULL REFERENCES ref_roles(role_name)` —
inventing a `ref_roles` table that does not exist and is not in this task's
DELIVERABLES. It looked right because an FK is the "proper" way to constrain a
role, and that is exactly why it slipped past: the reasonable-looking option is
the dangerous one.

Caught it before running anything. The replacement is a `CHECK` listing codex
00's six ladder roles, which is the pattern `ref_users.role` already uses.

That leaves the six roles written down twice — here and in `ref_users.role`,
which T-0004 widens to match. I documented the duplication in the migration
rather than abstracting it away, citing migration 014's precedent (the 5/50
variance thresholds are duplicated between SQL and `config.py` with a
keep-in-sync note). A shared roles table is a founder decision, not something to
introduce inside a task whose DELIVERABLES do not mention it.

A free-text column was the other option and I rejected it: a typo'd role assigns
the item to nobody, and the item then sits invisible forever. For the table
whose entire purpose is making work visible, that failure mode is disqualifying.

## AC-018 deserved more care than it first appeared to

"SHALL NOT open a duplicate while one is already open" reads like a `SELECT`
then an `INSERT`. It is not, and writing it that way would have been a race:
two callers sweeping the same population concurrently both see "nothing open"
and both insert.

The enforcement is a **partial unique index** on `(kind, subject_ref)
WHERE state IN ('open', 'in_progress')`, with `open_item` using `ON CONFLICT
... DO NOTHING`. The database decides, atomically.

Partial on the live states specifically, so that resolving an item frees the
subject to raise a fresh one later. A wage supplied and then removed has to be
able to reopen — a full unique index would suppress the second item forever and
the failure would be silent, which is the worst kind for this table.

**The test that matters most here is the one I nearly did not write.**
`open_item` swallows the conflict, so its callers never see an error, which
means `test_open_item_is_idempotent_while_one_is_open` passes *whether or not
the index exists* — the Python path returns `None` either way once the row
count comes back empty. So the idempotency test proves the contract but not the
mechanism. `test_raw_duplicate_insert_is_refused_by_the_index` inserts directly,
bypassing the helper, and asserts the database refuses by name
(`uq_worklist_open_subject`). Without the index that INSERT succeeds and AC-018
is enforced by convention alone.

That is the difference between testing that the code does the right thing and
testing that the right thing cannot be undone by the next person who writes raw
SQL against this table — and given every phase from B to E will write to it,
the second is what the AC actually needs.

## Deliberate design of `subject_ref`

`TEXT`, opaque, interpreted by the producer. Not a typed foreign key, because
subjects will span employees, deposits, chargebacks, certificates and store
tasks. The moment this table grows an `employee_id` column, Phase B's
reconcilers need their own, and the single pane stops being single.

The cost is real and stated: nothing at the database level guarantees a
`subject_ref` points at a live row. A person deleted out from under an open item
leaves an orphan. That is acceptable here only because codex 00 says nothing is
ever deleted — the orphan case cannot arise while that rule holds. If it ever
stops holding, this design needs revisiting, which is why the reasoning is in
the migration comment and not just here.

## Return types chosen to make sweeps quiet

`open_item` returns `None` rather than raising when an item is live, and
`resolve_item` returns `0` rather than raising when nothing is open. Both
because the callers are sweeps: `people.completeness` will walk a few hundred
people every night, and the overwhelmingly common outcome is "already has an
item" or "already fine". If those were exceptions the sweep would be
try/except noise, and the interesting cases would drown.

## What surprised me

That the migration's most valuable line is a `WHERE` clause. The partial index
is doing three jobs at once — enforcing AC-018, allowing reopen-after-resolve,
and keeping the worklist screen's primary read fast — and all three come from
the same four words. It took a rewrite to see that the state predicate was the
design rather than an optimisation.

Also: I ran the whole task on `main` and only branched at commit time. The gate
does not care, but the discipline says `forge/T-0003` from the start. Worth
noting because it is the kind of drift that is invisible until two tasks are in
flight at once.

## HALT — B-0022, raised after the pre-merge run

The code is done. The gate is not passable, and the reason is a defect in the
gate rather than in this task.

`scripts/schema_snapshot.py --diff` exits 1 on **any** drift, and `verify.sh`
treats a non-zero exit as a failed check. This task adds a table. Therefore
pre-merge is red, and would be red for every migration task forever — including
T-0004, which is nothing but a migration.

The check's own output already understands the problem. It prints:

> Schema drift is not automatically wrong — a migration is supposed to change
> the schema. It must be INTENDED: every line above should trace to a migration
> in this task, and the journal should say so.

It knows drift can be legitimate, tells the reader to confirm it against the
journal — and then has no way to record that anyone did, so it fails regardless.
Right intent, wrong mechanism. I wrote it in T-0000 and did not notice, because
T-0000, T-0001 and T-0002 changed no schema. The first task that touches a
migration is the first task that could have found it.

**Why I did not just fix it.** `scripts/verify.sh` and
`scripts/schema_snapshot.py` are not in this task's DELIVERABLES. Rule 4 —
BOUNDED SURFACE — is absolute, and the temptation here was strong precisely
because the fix is small and I am the one who broke it. A ten-minute edit to the
gate, made from inside a task that the gate is blocking, is self-certification
with extra steps: the thing asserting my work is correct would have been
modified by me, in the same commit, to stop objecting.

That is the whole reason the rule has no size exemption.
